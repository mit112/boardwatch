## Where this spec was wrong against the code

**1. T37's mechanism, and its fallback.** The handoff and D-472 both diagnosed starvation past
`busy_timeout` ("SQLite's busy handler is not fair… can starve past the timeout"), with the
fallback "raise the coordinator apply's busy_timeout, measured against the reproduction". Measured
before writing any fix: **starvation does not reproduce** — a back-to-back stream of short
transactions on one thread let a 200 / 2,000 / 20,000-insert writer on another in after
**0.003 / 0.039 / 0.160 s**. The real fault is a **WAL snapshot upgrade**: `apply_board` opens a
DEFERRED transaction and READS before it writes, so **one** commit from any other connection in
that gap fails the write with `SQLITE_BUSY_SNAPSHOT` (517) — the exact string run 3 reported — in
**0.0006 s against a 5,000 ms timeout**, never consulting the busy handler. **The prescribed
fallback is therefore not merely worse, it is impossible at any value.** It is pinned by a test
that asserts the ELAPSED TIME rather than the error. `store/db.py`'s `write_connection` docstring
already described this exact failure mode; it was not consulted.

**2. T37's consequence decision was not free.** The spec says "neither existing guard models the
pair", which is true, but not that
`test_a_fatally_refusing_run_still_lets_the_lane_thread_land_its_rows` **asserts** the behaviour
being removed. Choosing "a refused run lands no lane rows" required rewriting a shipped guard.

**3. T38's preferred design is a REGRESSION, not the smaller option.** The spec said "ship the
smaller one that passes the acceptance". Sized on the model D-344 was fitted to, recalibrated
against run 3: today 95.0 min, **static chain-first 105.5 min — worse than doing nothing**, ready
queue 83.8. Pulling a chain forward in a FIFO pool queue parks workers on a host whose lock is
already held. Only the dynamic dispatcher escapes it, which is what `host_diverse`'s own docstring
said when it declined to build it. **This supersedes D-344's "not built (the model already prices
the loss)".**

**4. T38's acceptance presumed a static order.** The shipped design has no static order — the
schedule is a function of completions — so the null control was re-expressed as an equal-cost drain
of the real `take_ready`, both arms over one fleet.

**5. T38's sizing undercounted the chain.** Not 1,931 requests: that is five boards' capped detail
counts. Run 3's smartrecruiters detail events across all ten boards are 1,947 plus ~362 listing
pages = **~2,309**, so the serial floor is **≥ 38 min, not ≥ 32**. Everything else in the
diagnosis held.

**6. T28's null control as specified was insufficient.** "The probe must find the funnel's 40
before grouping" — it does, and still returns 0. Finding the population does not show the GROUPING
can report a group. The first control tried was itself vacuous (pre- vs post-collapse: both 80, so
