Controls: Tenet3 #247643 answers 200 with 78,455 bytes; Cerebras #237110 answers 200 with 42,689
bytes. A dead Ashby page and a live one are both HTTP 200.

**(a) A jobapps-tree listing resets the board scanner's miss counter.** Twilio and Cohere are
watched boards whose `complete` scans today (149 and 141 postings) no longer list these ids, so
`_process_missing` incremented `consecutive_missing` — and an hour later the jobapps lane re-listed
both from the static directory and `_apply_listed` reset it to 0 (`scan/apply.py:212`) along with
`death_strikes` (`:218`). The docstring at `scan/apply.py:394-397` states the premise — "a listing
is positive evidence that the posting is ALIVE regardless of whose text arrived … a posting the
lane just watched being served" — and `lanes/jobapps.py:175` claims the lane "refreshes liveness
only". For this lane the premise is false: nothing is served; a directory is read. **2,481
jobapps-created rows exist; 2,478 are open; 3 have ever closed.** 90 of the open ones sit on
watched boards where the scanner's own evidence is being erased every run.

**(b) The URL death probe is blind to how Ashby and Greenhouse present a dead posting, and it
clears strikes when it looks.** `core/liveness.py` maps every 200 to `refetch_ok → alive`
(`verdict_for_status`); a 302 chain ending in 200 is likewise `alive`. So a probe of any of the
five above returns `alive` and zeroes `death_strikes` (`death_probe.py`, the `alive` branch). This
is consistent with D-325's own measurement (6.7% sensitivity; "every closed Workday requisition
still answers HTTP 200") — the class is now Ashby and Greenhouse too. The ATS list APIs, by
contrast, are authoritative and one GET per company: `api.ashbyhq.com/posting-api/job-board/{slug}`
and `boards-api.greenhouse.io/v1/boards/{slug}/jobs` both answered "absent" for all five.

**(c) The sweep never reaches them.** Run 433's log line: `death probe: 50 of 13101 due probed, 0
gone, 0 unknown, 0 closed (13051 refused by budget)`. The default `death_probe_budget = 50`
(`core/settings.py:344`) against a 13,101-row pool (12,027 never probed) is 0.4% coverage per run;
the ordering `last_death_probe_at ASC NULLS FIRST, id ASC` (`death_probe.py`, `candidates`) walks the
oldest ids first, so a row delivered this week is reached in roughly 260 runs. **Of today's 400
apply-lane leads, 300 sit on unwatched companies and 205 are jobapps-created; 393 have never been
death-probed.** That is the exposure the pre-flight sampled.

Cross-check that the fix reaches the queue: `review_gate.classify` reads `posting_closed` FIRST and
drains to `_closed` (D-383, `delivery/review_gate.py:203`), so anything T88–T90 closes leaves the
apply lane on the next reconcile with no delivery change.

## T89 — ATS list-API membership closes an unwatched registry-ATS posting

**Files:** `src/boardwatch/pipeline/death_probe.py` (`sweep_unwatched_deaths`, `CLOSING_SIGNAL`), `src/boardwatch/providers/ashby.py:42` and `greenhouse.py:61` (the list URLs already exist; Lever's is `api.lever.co/v0/postings/{slug}`), `src/boardwatch/reports/run_funnel.py` (`DeathProbeReport` gains per-signal counts), `src/boardwatch/pipeline/runner.py:1998-2018` (call site and console line).
**Design (settled here, so a cheap agent can build it):** split the unwatched pool by `companies.provider`. For a provider with a public list endpoint (`ashby`, `greenhouse`, `lever`; NOT `workday`, `jobapps`, `linkedin`, `indeed`), the probe unit is the **company**, not the posting: one GET of the list endpoint; a `provider_posting_id` absent from a parseable HTTP-200 listing earns a strike (`signal = "listing_absent"`), present clears it (`listing_present`), any non-200 / unparseable / empty-with-open-rows answer is `unknown` and neither increments nor resets (mirror `_empty_complete_is_evidence_of_nothing`, `scan/apply.py:504`). Two strikes in different runs close, `CLOSE_AFTER_MISSES` reused. Rows under these providers are **removed from the URL probe's candidate set** so each row is fed by exactly one signal and D-325 narrowing 4 holds without a second column. Rows under the other providers keep the URL probe unchanged. Budget is per company for the listing path (`death_probe_company_budget`, default 100 ≈ 100 s) and per posting for the URL path, both reported with `budget_refused`.
**Failing test first:** `tests/unit/test_death_probe.py` — an unwatched `ashby` company with two open postings; a stubbed listing that carries one id: the absent one gains a strike, the present one is cleared; a second run with the same listing closes the absent one and appends a `closed` event. A stubbed 500 leaves both untouched. A control: an unwatched `jobapps`-provider row is still probed by URL. Today the ashby row is URL-probed, reads `alive`, and can never close.
**Measure in the PR body:** run the new path once against the live store in a scratch copy (`BOARDWATCH_DATA_DIR`) and report closed / strike counts by provider; the expectation from §1.8 is that a large fraction of the 1,177 ashby + 1,415 greenhouse unwatched rows strike on the first pass. If it is small, the design is wrong somewhere — say so rather than ship.
**Traps:** the listing GET must go through `Fetcher` under the host's politeness lock (`core/politeness.py`), never a bare `httpx` call; Ashby's list is up to 1.7 MB for large boards (provider docstring D26) — do not store the payload, only test membership; Clera's board is 278 postings and unwatched, so this is also what eventually retires its 96 open rows. Do NOT promote these companies to `watched` instead — that ingests whole boards into the fleet (589 attempted today) and D-329 accepted the unwatched pool on purpose. The `jobapps`-provider rows (2,247 in the pool, 164 in today's apply lane) are tier-3 name-keyed rows with no ATS and stay on the URL probe; state that residual in the PR.

## 3. Owner decisions — not picked by default

**3.1 Visa-class specificity (§1.6, Sauna #204390).** The facts schema records `needs_sponsorship`
as a boolean and the catalog has `sponsorship_available` / `sponsorship_unavailable` as the whole
vocabulary. "Open to O-1 or J-1 sponsorship for exceptional candidates" is neither. Options: (a) add
a per-user fact `sponsorship_classes_acceptable` (a list; data, so multi-tenant) and a pattern
`sponsorship_limited_to_classes` capturing the offered classes, deciding `unmet` when the
intersection is empty — an engine change, after 09-19, and it ships a claim about visa law the
program has so far refused to make; (b) leave it to the judge, which already answered `low`
confidence and `seniority_fit = no` here. Sizing before ruling: count open `eligible` rows whose
body names a visa class (`O-1|J-1|TN|E-3|H-1B`) beside "sponsor" — not measured in this session.

**3.2 Defense employer as a hard stop (§1.7, ACS #237734).** The body states the company builds
weapon systems; the req itself is ERP work with no clearance or citizenship language, and the
judge's policy is explicitly six-family-only. A non-citizen can lawfully hold non-ITAR roles at a
defense contractor, so this is a preference, not an eligibility fact — and a `preference`-severity
family can never yield `ineligible` (D-388), only a review hold. If wanted: a `defense_employer`
family keyed on a small phrase catalog ("defense technology company", "weapon system", "warfighter",
"defense contractor") that HOLDS for review. False-positive risk: aerospace and dual-use employers
(Relativity, Cerebras) describe themselves in adjacent words. Rule before anything is built.

**3.3 Per-company posting-volume / title-entropy signal (§1.3, Clera).** Nothing in the store
measures a company's open count against its title diversity. A heuristic ("> N open rows sharing a
normalised title", "same title in > M cities") would have flagged Clera (96 open rows here, 278
live) — and Western Digital (36 identical titles, 36 real requisitions, D-327). Whether a board-level
low-trust flag that holds for review is worth that false-positive class is a policy call; note the
three Clera leads were already held for review on seniority, so the marginal value today is zero.

**3.4 Compensation as a seniority input (§1.5).** 580 open rows carry a structured salary and 140
have `salary_min ≥ $200k`; none of it is read. Feeding a profile-relative ceiling into
`seniority_above_band` would be a deterministic sibling of the judge's body reading, which D-477
declined for body prose. The judge caught this case. Rule whether a structured salary is different
enough from prose to warrant the family.

**3.5 Does a provider-authored structured field count as "the frozen JD"?** T92 depends on it.
Today the invariant is written for spans of `body_text`. If a structured field may decide, T92 can
yield `ineligible` with the field as its locator; if not, it holds for review. Same question will
recur for `department` ("Participant Recruitment") and `employmentType`.

**3.6 The findings doc must not be committed as written.** It records the owner's visa status and
nationality in prose. Strip those sentences (refer to "the profile's declared work-authorisation
facts") before `git add`, or keep it under `.agent/`.
