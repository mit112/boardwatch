## T1 — pysqlite `begin` hook

**Files:** `src/boardwatch/store/db.py` (`get_engine`, and the second engine at ~145); `src/boardwatch/cli/notify_cmd.py:54`, `src/boardwatch/cli/digest_cmd.py:62` (remove the hand `BEGIN IMMEDIATE`, which would double-BEGIN once the hook exists).
**Change:** the SQLAlchemy-documented pair — on `connect`, `dbapi_connection.isolation_level = None`; on `begin`, `conn.exec_driver_sql("BEGIN")`. Consider `BEGIN IMMEDIATE` for `engine.begin()` blocks that write (the runner, the ledger) so writers queue on `busy_timeout` instead of failing at commit; keep plain `BEGIN` for `engine.connect()` reads.
**Failing test first:** `tests/unit/test_store.py::test_reads_inside_one_transaction_share_a_snapshot` — engine A opens `engine.begin()`, reads a count, engine B (second `get_engine` on the same file) inserts and commits, engine A reads the count again inside the same block: must be equal. Today it is not (WAL gives each autocommit SELECT its own snapshot). Also re-run the D-426 `seeds` reproduction from memory `two-reads-on-sqlite-are-two-snapshots`.
**Traps:** Alembic builds its own engine from the URL (`ensure_schema` comment) — decide whether migrations get the hook too (`env.py`); `PRAGMA journal_mode=WAL` must still run outside a transaction (it does, on `connect`). Watch for "cannot start a transaction within a transaction" anywhere that already emits BEGIN by hand. Run the two-writer concurrency test (`test_two_writer_concurrency`) several times, not once.
