## #2 — T113 (RE-SCOPED) · Automatic, bounded refresh of the standing queue's gate readings

**The original ticket** is `TICKETS-2026-09-19-ASTRA-02.md` §T113 (stale gate NEGATIVES suppressing
their own repair; `top_cmd` hides and promotes on a historical read). **2026-09-22 widened it.** A
stale reading is not only a negative that suppresses; every re-key also strands the POSITIVES that
0-B's promotion needs.
- The original sizing was 97 of 984 standing leads with no current gate row. After run 470 it was
  **947 of 987**.
- The repair was done by hand (D-548) with `rejudge_backlog.py`. That script is the manual form of
  this ticket.

**What to build (design first, then code).**
- A refresh step in the daily run, after the gate judges the depth slate:
  - Take standing-queue leads (§0's population) that have **no current gate reading** under the
    gate's freshness key.
  - Judge them through the SAME `run_gate_stage` (it accepts any objects with `posting_id`) within
    a **per-run budget**.
  - Order **promotable holds first** (`no_requirements_found`, `experience_requirement`, the two
    holds a judge `eligible` releases), then the apply lane, then the rest.
- **Budget** is a new `[gate]` setting. `0` means off, and that is the multi-tenant default.
  - It is a scheduling knob, so it belongs OUT of `config_hash`, like `depth`. It changes which
    leads carry a verdict at the lane split, so it goes INTO `_ROUTING_RELEVANT`.
  - It is a new `Settings` field, so it has **four gated registration sites**: `cli/config_cmd.py`
    `_GATE_KEYS`; `tools/generalization/snapshots.py` (both dicts, plus the field class);
    `reports/manifest.py`; `core/settings.py`. `make check` catches a miss; narrow pytest does not.
- **Funnel.** Report it in the funnel's `gate` block: `refresh_candidates`, `refresh_sent`,
  `refresh_pending_after`.
  - Pending staying high across runs is the signal that the budget cannot keep up.
  - Any soft alert must sit ABOVE `_emit_morning` (the finalize-block ordering invariant).
- **Chunk the writes.** `run_gate_stage` commits once at the end, so call it per chunk. A timeout
  or kill must not discard a whole refresh.
- **The original half still stands.** `top_cmd` hides on a historical `ineligible` and promotes on a
  historical `eligible` (the T113 text cites `top_cmd.py:540-545`, `:700-703`, `:724-728`; line
  numbers drift, so re-find them). A stale negative should become a review hold pending re-read,
  not a suppression.

**Size, from the 2026-09-22 calibration.**
- A full standing queue is ~833 leads, about 64 calls at 13 per call: ~30–40% of the seat in one go.
- A budget of ~130 per run (10 calls, ~5–7% of the seat per run) drains a full re-key in about 7 runs.
- In steady state (no re-key) the refresh is near 0.

**Interactions.**
- **T152** removes `rules_hash` from the SENIORITY reading's key, so rules-only edits stop killing
  seniority readings. Verdict rows stay identity-keyed, so T113 is still needed.
- **T155** adds `effort` to the freshness key; T113 should respect whatever key exists.
- **Fail direction.** D-380 still holds: absent reads `unclear`/no promotion, never `no`.
- **Tests to keep green:** `tests/unit/test_rank_gate_filter.py:142`, `:116`, and
  `tests/unit/test_rank_verdict_tiers.py:107,136,153`. Also the `lane_decision` AST guard, which
  enumerates the five call sites.

**Discriminating tests owed.**
1. A fixture re-key followed by a run: the refresh restores a 0-B promotion that the re-key demoted.
2. The budget is respected.
3. Order: promotable holds come first.
4. A failed batch leaves its leads pending, never dropped.
5. Budget `0` means no refresh at all. This is the multi-tenant default.

**Done when.** A re-key's standing-queue damage heals without a hand-run script, within a stated
number of runs, visible in the funnel.

### T350 — what breaks before requests at 2–5x boards: scan-preparation memory and store growth

posting ids in one `.all()` and builds a frozenset per board before dispatch; at 5x boards that set is resident for the

51.21 GB on 2026-11-24 (funnel `store_size`),
growing about 158 MB a day (Nov 19–24, DERIVED), with 122 GiB free on the SSD; at the same retained rows per board, 10k
boards is about 100 GB. Track rows and bytes retained per night before choosing a remedy (R-009 sized the options).

**Item (1), expanded 2026-11-24: load known ids only for boards that read them, when they enter dispatch.**
- **Trigger:** every scan, during preparation in `_scan_body`.
- **Current behavior (verified at 1971c401):** [`scan/coordinator.py:511-522`][bw-coord-known] runs one `SELECT` of
  every open `(company_id, provider_posting_id)` for all selected boards into `grouped` (a dict of sets), then

  3. Only if step 2 is measured insufficient: page-scoped lookup, as Opportun's Workday adapter asks

- **Local versus dependency:** all of it is Boardwatch code and SQLite. Opportun (Apache-2.0) is evidence for the

- **Assumptions:** the per-board query is index-served on the live store (check with `EXPLAIN QUERY PLAN` on a clone);

  next submit by more than it saves.
- **Smallest offline replay (benchmark):** two fixture stores built from one seed, at 1× and 5× today's fleet (5,170 and

### T351 — Workday: split a censored full listing by facet, inside the board's own scope
- **Trigger:** a full (reconciliation) Workday listing whose offset-0 page reports `total` = 2,000, the censor, for an
  unsliced board or for a manual slice (`host/tenant/site#group=Descriptor`). Never on a head scan (T340).
- **Current behavior (verified):** the pager stops when the offset wraps at 2,000 and a full page adds no new
  `externalPath` ([`providers/workday.py:787-797`][bw-wd-wrap]); `_uncapped_total` records the facet sum
  ([`:565`][bw-wd-uncapped], note at [`:808`][bw-wd-censor-note]); the board is `partial`, so `apply_board` closes
  nothing ([`scan/apply.py:98-164`][bw-apply-status]). A board over the censor is therefore `partial` every night and
  none of its postings can ever close through the listing. The only remedy today is a manual slice
  (property 6, [`:44-67`][bw-wd-p6]; `boardwatch companies facets`), which is a separate `companies` row: its own
  inventory, closures and coverage, so N slices plus an unwatched root are N boards, not one.
- **Measured exposure:** in the saved T338 replay, `genpt.wd1.myworkdayjobs.com/genpt/Careers` read 1,999 rows against a
  facet sum of 2,659 (`.agent/2026-11-24-t338/full.jsonl` line 160). On run 2899, **13 censored Workday boards report
  101,842 postings by facet sum and enumerate 25,880.** The largest: Accenture 65,239 / 1,919; JLL 8,391 / 2,000;
  Hitachi 4,150 / 2,000; Airbus 3,008 / 2,000. Nine of the 13 are between 2,076 and 2,656 by facet sum (genpt, Mass
  General Brigham, Jabil, Tapestry, Driven Brands, Abbott, Sentara, ABB, Interpublic): 21,054 reported against
  17,961 enumerated. genpt has never had a complete scan and holds 5,347 open postings against 2,656 live (Jabil's last
  complete scan was run 550). Caveat: `_facet_sum` takes the maximum over every facet ([`:342`][bw-wd-facetsum]); a
  multi-valued facet would overstate the size, so the facet sums are an upper bound until each tenant is checked.
- **Not this ticket:** CVS (18,402 / 3,000), Lowe's (12,907 / 3,000), DaVita (3,260 / 3,000) and RTX (4,408 / 2,999)
  are not censored. Every row is reachable by paging, and Boardwatch's own 150-page backstop stops them
  ([`:101-109`][bw-wd-maxpages], "DO NOT RAISE IT"). Raising that backstop is a cost decision for the owner.
- **Proposed change (Boardwatch terms), all in `WorkdayProvider.fetch_board`, one board, one snapshot:**
  1. The root query is the board's own scope: no `appliedFacets` for an unsliced slug, or the slice's resolved
     `{group: [id]}` for a sliced one. Read its offset-0 page as today. If it is not censored, page it as today and
     stop. If it is censored, do not page the root further (its rows past offset 0 are re-read in the children), as
     Stapply's `_exhaust_query` does.
  2. If the root is censored, plan a split from the root page's facets (already read; `facet_buckets`): candidate groups
     not already applied, with at least two non-empty values. A group is **exhaustive** when its value counts sum to at
     least the parent's size; prefer exhaustive single-valued groups (`jobFamilyGroup`, `timeType`, then the location
     groups nested under `locationMainGroup`), as Stapply does.
  3. Each child query is the parent's `appliedFacets` plus one value. Page it to a short page. A child that is itself
     censored is split again on a group not yet applied, up to a fixed depth. Every row from every leaf joins one
     `by_id`, deduplicated by the posting id, so the board's `listed_ids`, closures, gate and detail phase are exactly
     today's, over the union.
  4. **Completeness certificate.** The snapshot is `complete` only if ALL of these hold: every split group was exhaustive;
     every leaf ended on a short page (not the wrap, not the backstop) with an uncensored `total`; every leaf enumerated at
     least its own `total` in distinct ids; no child request failed; the deadline (T243's `detail_phase_stops`, the board
     cap) did not cut the plan; and the union holds at least the root's size. Any miss makes it `partial`, which closes
     nothing. **A union count that matches the facet sum is necessary, never sufficient.**
  5. Budget: the whole split, children included, stays within the existing `_MAX_PAGES` (150 pages). If the plan
     computed from the facet counts exceeds it, the board is read as today and the error names the plan's page count.
     That covers the nine boards under 2,700; Accenture, JLL, Hitachi and Airbus stay partial until the owner rules on a
     larger budget for split boards.
  6. T340 stays separate: a head scan never splits. A split sweep has no single newest-first order, so it records
     `head_pages` and `head_missed` as NULL; the head scan's own nights measure the stop point. `listing_pages` counts
     every page, children included (T343 reads cost from it).
- **Upstream evidence (Stapply, `kalil0321/ats-scrapers` at `82662ad1`, MIT):** recursive facet subdivision in
  [`_exhaust_query`][sa-wd-exhaust], facet choice and the 99% coverage rule in [`_pick_subdivision_facet`][sa-wd-pick],
  nested location facets in [`_facet_values`][sa-wd-values], the priority list in [`_SUBDIVISION_FACETS`][sa-wd-prio].
  Tests: [a facet that misses jobs is a last resort][sa-t-miss], [the board root size is the largest single-value
  facet][sa-t-rootsize], [a capped board split by country then city][sa-t-split], [the root split skips a facet that misses
  jobs][sa-t-rootskip], [a capped search with nothing left to split][sa-t-nothing]. **What Stapply does not do, and
  Boardwatch must:** it takes a still-capped leaf's 2,000 rows and only logs a warning, and it falls back to a
  non-exhaustive facet with a warning. Stapply has no closure semantics, so neither matters to it; here both must make
  the board `partial`. Its own comments disagree on whether `workerSubType` is single-valued (multi-tag at lines
  138-143, listed in `_SINGLE_VALUE_FACETS` at line 159), so the size estimate is checked per tenant, not trusted.
  Stapply runs the children concurrently under a semaphore. Here they stay serial on the tenant's one host lock
  (`core/politeness.Fetcher`).
- **Local versus dependency:** all local. The CXS endpoint and its facet catalog are Workday's; nothing new is installed.
- **Assumptions:** child totals are uncensored when under 2,000 and their facet counts drift by a few rows between
  requests (Stapply's 1% tolerance is for planning only; certification needs the exact checks in step 4); `appliedFacets`
  with two groups is an AND (verify on genpt with three requests).
- **Smallest offline replay:** a fake CXS transport over a planted 2,600-row board with two group dimensions, censoring
  `total` at 2,000 and wrapping offsets past it, as the live service does; plus a fixture of genpt's real first page if one
  is captured. Run the blind pager and the split pager over it with the same request budget.
- **Acceptance (offline, before any live run):**
  1. **Exact expected ids:** on the planted board, `listed_ids` equals the planted set exactly: no row missing, none
     doubled where a row sits under two values of a multi-valued group.
  2. **Yield at equal budget:** at the same request budget, accepted ids (through the real `build_listing_gate`) per 100
     requests for the split pager and for today's pager are reported side by side; the split pager is not lower.
  3. **Two-cycle false-closure test:** the store holds an open sentinel listed only in child C. C answers HTTP 500 (one
     variant) or falls past the budget (another) on two consecutive scans. After both, the sentinel is open with
     `consecutive_missing` 0 and no `closed` event. Null control: the same fixture with C readable and the sentinel absent
     from C closes it after two scans, so the test can fail.
  4. A non-exhaustive split group, a censored leaf with nothing left to split, and a union that matches the facet sum while
     one leaf ended on the wrap each yield `partial`.
  5. A sliced board's split never reads outside its slice: every child request carries the slice's facet.
  6. An unsliced board with `total` under 2,000 sends exactly today's requests (no split).
- **Live check after merge:** the first nightly records enumerated against reported per split board. The first two
  complete sweeps of a split board close what the board stopped listing long ago (genpt: about 2,700 by the store's open

- **Projected cost (DERIVED):** the nine boards list 21,054 rows, about 1,050 pages plus one partial page per child,

  tenant's child count, which is unknown until their facets are read.
- **Depends on:** nothing to build. Best landed before T340 is armed, so the rotating full sweep can certify these boards.
- **Result (2026-11-24, D-708):** built as above, with three departures recorded in D-708: the plan is chosen by cost,

### T353 — resume an interrupted pipeline scan from the boards it already committed
- **Trigger:** a pipeline scan killed or aborted after some boards committed (SIGINT/SIGTERM, `kill -9`, power or sleep,
  a crash), followed by the operator's retry the same night.
- **Current behavior (verified):** each board's apply is one transaction with its `board_scans` row
  ([`scan/apply.py:98`][bw-apply-txn]), so a board is either fully applied or untouched. The abort handler closes the run
  row as failed ([`scan/coordinator.py:477-490`][bw-coord-abort]). A retry calls `insert_run` and reads the whole watched
  fleet again ([`:460-470`][bw-coord-insert]), so it fetches every board again. Four consequences, from the code:
  (a) every completed board pays its listing again; (b) **a posting absent from a board that completed before the kill
  takes a second miss on the retry**, because `_process_missing` ([`:621-666`][bw-apply-missing]) counts one miss per
  `complete` apply with no per-night guard and `CLOSE_AFTER_MISSES` is 2 ([`:54`][bw-apply-close]): one absence seen twice
  in one night closes the posting; (c) `_armed_listing_gate` truncates `listing_gated.jsonl` at scan start
  ([`:213`][bw-coord-audit]), so the retry erases the killed run's gate trace; (d) readers that count scans per night
  (`dead_for_three_scans`, T334's guarded nights) see two runs for one night.
- **Measured exposure:** none of the 20 runs that carry pipeline scan rows since 2026-09-03 ended unfinished or failed
  (live store, read-only). The exposure is per incident: a full rescan, plus one early closure risk per absent posting

- **Proposed change (board-level only; no cursor inside a board):**

  3. **Which run:** the newest run that has a manifest, no `scan_finalized_at`, pipeline board scans (never a CLI row), and

  6. Out of scope: resuming the lane stage that overlaps the scan (it reruns from scratch, as it does on a retry today:

### T354 — retry a failed Workday detail from the stored listing row, not by rediscovering it
- **Trigger:** a Workday listing succeeds and the detail GET for an unknown row fails (HTTP error or malformed payload,
  [`providers/workday.py:854-880`][bw-wd-detail]), or the detail phase defers the row (budget or T243 stop).
- **Current behavior (verified):** the failure is an error line and the board turns `partial`; nothing about the row is
  stored. The row is never a posting, so the next scan finds it unknown again only if the listing lists it within what is
  read. Today that is the whole listing every night. Under T340's head scan, a row with an old date that has moved past the
  stop point is read again only on the rotating full sweep (up to N nights). A posting that fails its detail every night
  is retried every night with no cooldown. If every detail of a board fails, the whole board is `failed` and its listing
  evidence is discarded.
- **Measured exposure (live store, read-only):** 3, 0 and 4 failed Workday detail reads on runs 2899, 2887 and 2882 (Intel,
  Manulife; one board on run 2887 failed every detail); `detail_deferred` 0 on all three. **Small today, because every
  night reads the full listing.** The ticket's value arrives with T340's head scan and grows with fleet size.
- **Proposed change:**
  1. A **pending-detail record** per `(company_id, provider_posting_id)`: the listing row as served (title, locations,
     posted date, `externalPath`, bullet fields: what `parse_posting(host, site, row, detail)` needs), the kind (`failed` or
     `deferred`), the first sighting time from the listing, the number of failed nights, the last try and the last error's
     typed status. It is not a `postings` row, so ranking, eligibility and delivery never see it: nothing scores a
     posting with no evidence.
  2. **Re-entry path:** the coordinator hands a board's pending records to the provider in `BoardRequest`. After the board's
     own new rows have had their details, the provider retries pending ones by direct GET of
     `https://{host}/wday/cxs/{tenant}/{site}{externalPath}`, under the same host lock and pacing. Budget: at most 20 a board
     a night (Opportun's per-host figure), and only what is left of `detail_fetch_budget`, so later valid postings always
     go first.
  3. **Cooldown and drain, as ApplYourself's failed reads:** after 3 failed nights, retry once every 7 days. Drop the
     record when the detail answers gone (404/410), after 14 days in total (Opportun's age bound), or when a full sweep no
     longer lists the id. The full sweep is the drain; a record never outlives the listing.
  4. **A detail read alone never closes or reopens:** a healed detail inserts the posting with `first_seen_at` and
     `last_seen_at` taken from the listing sighting the record holds, never from the detail read's time: a detail read is
     not a sighting, the rule `apply_refetched` already follows ([`scan/apply.py:167-189`][bw-apply-refetch]). A gone
     answer only drops the record. If the id belongs to a closed posting (a relisted id, which is unknown because known ids are open ones), the healed detail adds a version and
     leaves it closed; the next listing sighting reopens it as today.
  5. Provider-neutral record, Workday first. SmartRecruiters and Oracle detail URLs are rebuilt from the id alone, and
     T348's "keep deferred details pending before the window advances" needs the same record.
- **Upstream evidence:** Opportun (`bgoleno/opportun` at `aac0ad24`, Apache-2.0): [`jobs/retryWorkdayCapture.ts`][op-retry]
  rebuilds the detail target from the stored posting URL, retries under a per-host cap of 20 a run and moves a row past
  14 days to a terminal state without a fetch ([bounds][op-retry-bounds], [loop][op-retry-loop]); its tests cover a heal, a
  still-failing row, the age bound, a throw that does not stop the sweep, and the per-host cap
  ([`retryWorkdayCapture.test.ts`][op-retry-test]). ApplYourself at `c5dfda78`, MIT:
  [`feed/failed_reads.py`][ay-failed] keeps failures across nights, skips a posting after `max_failures` until
  `retry_days` pass, marks 404 as gone and forgets old entries. Boardwatch differs from both: Opportun stores the bare
  posting and retries it in a separate daily job; here the retry rides on the board's own scan, so it shares the board's
  host lock and pacing and never competes with that tenant's own scan for the host.
- **Local versus dependency:** all local (one additive table). Workday's detail endpoint is the one already used.
- **Assumptions:** an `externalPath` stays valid for the life of a requisition (the id is derived from it, property 5);
  the 3/7/14 numbers are starting constants to revisit after a month of records, not settings.
- **Smallest offline replay:** a fake tenant whose detail for row R answers 500 on night 1 and 200 on night 2, with R
  moved past the head-scan stop point on night 2 (T340 armed in the fixture), and a restart (new process, same scratch
  store) between the nights. A second board holds a new valid posting V on night 2.
- **Acceptance:** R is stored on night 2 with **one** detail request and no listing page beyond the head; V is
  detail-fetched before R; requests per recovered JD are counted and reported; R never enters ranking or eligibility
  before night 2; neither night closes or reopens anything because of a detail read; a record for an id the next full
  sweep does not list is dropped and closes nothing; a detail that keeps failing follows the cooldown (3 tries, then one
  a week, gone at 14 days).
- **Depends on:** T340 (its value is the head scan's gap; land before or with T340's arming, which D-707 holds until
  seven shadow nights). Shares its record with T348.

### T355 — bind a stored HTTP validator to the listing gate it was learned under
- **Trigger:** a provider that discards unstored rows through the listing gate commits a validator on a `complete` scan,
  and a later scan sends it under a different gate (a profile edit, a taxonomy edit, a `location_filter_mode` change, the
  gate switched off), so a 304 answers before the new gate sees the rows the old one rejected.
- **Current behavior (verified):** SmartRecruiters sends the stored validator ([`providers/smartrecruiters.py:132-143`][bw-sr-fetch]);
  a 304 becomes `unchanged`, which skips the gate and the board's inventory. A `complete` snapshot persists the ETag
  ([`scan/apply.py:155`][bw-apply-validators], [`:669-690`][bw-apply-persist]) though `apply_listing_gate` discarded
  the rejected rows unstored ([`providers/base.py:128`][bw-base-gate]). `get_validators` keys on the URL alone and expires
  at `validator_max_age_hours` (default 24) ([`store/queries.py:444-466`][bw-q-validators]); `http_cache` has no gate column
  ([`store/tables.py:428-435`][bw-t-cache]).
- **Measured exposure (live store, read-only):** **175 of 177 SmartRecruiters boards hold an ETag.** No Workday, Oracle,
  Apple or Eightfold URL holds one (Workday property 3: the CXS POST sends none). On the four nightlies 2026-11-21 to 24,
  **13, 127, 16 and 65** SmartRecruiters boards answered 304: a nightly reaches a board just under 24 hours after its stored
  `fetched_at`, so the exposure is not only a same-day rerun. A gate change between two nightlies hides the newly
  admitted rows on that night's 304 boards for one night. The next night the validator is older than 24 hours
  (`unchanged` does not refresh it), so the board is read in full. Within a day, a rerun can be blind for up to 24 hours.
- **Proposed change:** one function computes the gate key, a digest of what `build_listing_gate` reads (the profile view,
  the role taxonomy, `location_filter_mode`), with a fixed constant for "gate off". T339's `gate_key` uses the same
  function. `BoardRequest` carries the key and the snapshot echoes it. `_persist_validators` stores it in a new nullable
  `http_cache.gate_key` (additive migration). `get_validators` returns no validator for a gating provider unless the
  stored key equals the request's; a legacy row (NULL key) never matches for a gating provider, so it costs one full read
  and is then rewritten with its key. Any key change, including the gate switched on, costs one full read; that is the
  cheaper mistake. Gating providers declare it (the six that call `apply_listing_gate`). Greenhouse,
  Ashby, Lever, Workable, Amazon and Jibe ignore the key, so their 304s are kept.
- **Upstream evidence (ApplyPack, `applypack/applypack` at `38639ddd`, MIT):** rule 4 of
  [`src/fetchers/conditional.ts`][ap-rule4], "a validator is only sent under the rules it was learned under", stored as
  `rules` on the [entry][ap-entry] and compared in [`conditionalHeaders`][ap-headers]; a row from before the rules were
  recorded reads `rules: null` and never matches ([`readValidator`][ap-read]). Tests: [sent while the rules hold and not
  once they change][ap-t-rules], [holds again after the full read under the new rules][ap-t-holds], [a row kept before
  the rules were recorded is read in full once][ap-t-legacy]. ApplyPack keeps validators in process memory plus the
  company row. Here they stay in `http_cache`, committed in the board's transaction (D22), which already gives ApplyPack's
  rule 3 (commit only once the jobs are stored).
- **Local versus dependency:** all local.
- **Assumptions:** the gate's inputs are exactly those three (re-read `_armed_listing_gate`, [`scan/coordinator.py:201-218`][bw-coord-gate],
  and `rank/listing_gate.build_listing_gate` when building; a missed input is a silent bypass); SmartRecruiters' list ETag
  changes when the listing changes.
- **Smallest offline replay:** an unchanged SmartRecruiters payload behind a fake transport that answers 304 exactly
  when `If-None-Match` matches. Three passes on one scratch store with a restart between each: gate A rejects row R; gate
  B accepts R; gate B again.
- **Acceptance:** pass 2 sends no `If-None-Match`, gets 200, detail-fetches and stores R (**recovered on the second
  pass**); pass 3 sends it, gets 304, makes zero detail requests (**conditional reuse on the third**); zero closures and
  zero `consecutive_missing` changes across all three. Gate on → off sends no validator on the first ungated pass. A
  legacy row with a NULL key under an armed gate gets one full read, then reuse. A non-gating provider's validator is sent
  exactly as today. The recovery and gate-off assertions are each checked to fail against today's code.
- **Depends on:** nothing. Shares the gate-key function with T339 and T353.
- **Result (2026-11-24):** built as above with T353's `listing_gate_key` (`LISTING_GATE_OFF_KEY` for no gate), one
  additive migration (`p_http_cache_gate_key`) and a `gates_listings` declaration on the six providers that call
  `apply_listing_gate` (a test holds it to exactly those). One departure: the coordinator passes the scan's key to
  `apply_board` beside the snapshot instead of having each provider echo it through `BoardSnapshot`, which would touch
  every provider for a value only the coordinator holds. Offline replay (`tests/pipeline/test_validator_gate_key.py`,
  a fresh engine per pass on one store): pass 2 sends no `If-None-Match`, gets 200 and stores R with one detail read;
  pass 3 sends it, gets 304 and makes zero detail reads; no closure or `consecutive_missing` change in any pass. Gate on
  to off sends no validator; a NULL-key row is read in full once, then reused; Greenhouse keeps its validator across a
  gate change. With today's lookup restored, the recovery, gate-off and legacy tests fail; 5 mutations, all caught.
  Review round 1 (no blockers): the key now also digests `rank/`, so a release that relaxes a veto does not reuse a
  validator learned under the stricter one; a unit test moves the key with each input alone (profile field, taxonomy,
  location mode, code), each removal caught.

## Added 2026-11-26 — follow-ups from the 2026-11-25 coverage work (D-711, D-712)

### T356 — an ATS-sourced board name can carry the board's furniture, and a renamed board can collide with another
`common_crawl.employer_name` (D-711) takes Greenhouse `company_name`, SmartRecruiters `company.name` and the Workable
account name as given, with only whitespace cleaned (`_clean_name`). Ashby titles lose `_BOARD_SUFFIX`; the others do
not. Measured 2026-11-25 on the maintainer's store, renaming 666 slug-named crawl boards to their ATS names: 651
resolved; 18 carried furniture (`Careers`, `Job Board`, `(Website)`, `Referral Board`, e.g. "Radix Trading Experienced
Job Board") and were held by hand; 10 normalized to a different watched board's company (e.g. Bespoke Labs against
Bespoke Technologies, Capital Technology Group against Capital Group) and were held too. **Fix:** strip the same
furniture from every provider's name, not only Ashby's, with the measured strings as the test cases; propose a board
whose name collides with a watched company with that collision named in the output, never silently. The 28 held boards
need a read once the strip exists. Size: small.
**Result (2026-11-26):** built. `_clean_name` strips one catalog of furniture for every provider (Ashby's old
`Jobs|Careers` suffix is inside it). Measured on the 363 crawl-cohort Greenhouse and Ashby boards the 11-25 rename left
slug-named (349 answered): 14 Greenhouse names change, no Ashby name does. Left alone on purpose: "24 Hour Home Care -
Corporate Division", "CTC Lateral - Website & LinkedIn" and the qualifier in "Radix Trading Experienced Job Board" (now
"Radix Trading Experienced"). A " - " segment is stripped only when it ends in furniture. The collision line reads
watched boards only: an unwatched lane row with the same name is not a board.

### T357 — a TikTok posting link not shaped `search/{id}` takes the lane's tier-2 identity
`lanes/dereference._tiktok_posting_target` reads only `lifeattiktok.com/search/{id}` onto the `tiktok:tiktok` board's
posting key (D-712), and refuses any other path, so such a link falls back to `posting_identity` tier 2 and cannot
group with the board's own row. None in the store on 2026-11-25. **Fix when one appears:** capture the shape from the
link, map it if it carries the posting id, and add it to the deref tests. Size: trivial, measure first.

### T358 — ByteDance's careers site is a separate API from TikTok's
`joinbytedance.com` postings (about 44 built leads, through the lanes only, measured 2026-11-25) are not on
lifeattiktok.com, so the `tiktok` provider (D-712) does not reach them. The site's listing API was not found in the
D-712 work. **Next step:** find and size the public listing endpoint (whole-board request, posting date, body inline),
then decide whether it is a second slug of the `tiktok` provider or its own provider. Size: medium.
**Result (2026-11-26, D-713):** built as a second slug. joinbytedance.com is the same API's `website-path: en`
tenant (1,405 postings, 600 US, identical shape); the board is `tiktok:bytedance`, and its links dereference onto
it. Not watched: the owner's call.

### T359 — size Avature before iCIMS and SuccessFactors (amends T347's order)
T347 orders iCIMS and SuccessFactors first because each covers more than one large employer. Built leads that reached
the pipeline through the lanes only, measured 2026-11-25, put **IBM on Avature at about 93**, ahead of every iCIMS or
SuccessFactors employer in that list (Delta, MetLife and Bloomberg are Avature too). **Next step:** size an Avature
provider on IBM first: the listing and detail endpoints, paging, whether the posting date is listed, and whether one
provider reaches the other three tenants. Size: one provider, medium.
**Result (2026-11-26): blocked, not buildable as an HTTP provider.** `careers.ibm.com` (Avature) answers every
listing, detail, feed and per-locale sitemap request with `202`, an empty body and `x-amzn-waf-action: challenge`
(AWS WAF's JavaScript challenge); only `robots.txt` and the sitemap index answer 200. `delta.avature.net` answers the
same challenge. Passing it needs a browser, which boardwatch does not run. The store holds 921 postings on IBM's URLs, all
through the lanes, and the lanes stay the only route. T347's order (iCIMS and SuccessFactors first) stands. Reopen only if
a tenant is found that serves its listing without the challenge.
